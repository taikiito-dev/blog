エンジニアではない。2025年から、家族のデータを他人のサーバーから自分で借りたサーバーへ移し、それ以来ずっと運用している。

構築の手順書はすでに世の中にあり、自分が書いても上手くならない。ここに書くのは別の半分、つまり運用して壊した話だ。11件ある。全部同じ形をしている。道具が「成功」と報告した。それを信じた。報告は狭い意味では本当で、肝心な意味では嘘だった。

動かしているもの#

VPS（Virtual Private Server = 業者のデータセンターにある自分専用のLinuxマシン）1台。6vCPU / 12GB RAM で月$10弱。Docker Compose、nginxのリバースプロキシ、そしてCloudflare Tunnel。トンネルは外向きの接続しか使わないので、サーバー側のポートを内向きに開ける必要がない。

その上に、写真はImmich、ファイル同期はNextcloud、パスワードはVaultwarden、予定表と住所録はRadicale、ログイン統合（SSO = Single Sign-On、1回のログインで複数サービスに入れる仕組み）はAuthentik、gitサーバーはForgejo、死活監視はUptime Kuma、あとは自分で書いたWebアプリ。常用者は2人。

バックアップは毎晩、rcloneでBackblaze B2（安価なオブジェクトストレージ）へ暗号化して送っている。メールも約53,000通を自分の持っているドメインへ移した。

以下、壊した順ではなく、話の通りがいい順に並べる。

1. 黙って止まっていたバックアップスクリプト#

症状　サーバーを移行するとき、写真46件が、これから捨てる側のマシンにしか存在しないことが分かった。

信じていたこと　毎晩のrcloneバックアップは何か月も動いている。終了している。警告も来ていない。だから全部取れている。

実際に真だったこと　スクリプトの先頭に set -e が書いてあった。途中の1ステップが失敗し、set -e は設計どおりの仕事をした。つまりスクリプトを止めた。それ以降のステップは毎晩まったく実行されていなかった。 静かに。このスクリプトの「成功」は、自分が気づくようなクラッシュが起きなかった、という意味しかなかった。

どう気づいたか　監視からではない。移行作業中に2台のファイル数を手で数えて比べたから。たまたま見ていたからだ。

直し　各ステップが自分の結果を報告し、最後に「全部OK」か「失敗あり」のどちらかを必ず印字する形に書き換えた。最初の失敗で止めるのをやめ、全部試してから何が駄目だったかを教えてもらう。set -e は出力を人間が読むスクリプトには正しい。夜中の2時に自分が寝ている間に走るスクリプトには、はっきり危険だ。

一般化　復元したことのないバックアップはバックアップではない。そして失敗の signal が「プロセスが落ちたか」だけの自動処理は、監視されていない。自動処理には必ずこう問う — この中の1ステップが昨夜失敗していたら、自分はどうやって知るのか。 「知らないままになる」が答えなら、その自動処理は飾りだ。

2. ファイルを消して「成功」を返した同期コマンド#

症状　いつもの rclone sync のあと、コピー先にあったファイルが消えた。

信じていたこと　sync は「コピー先を元と同じ状態にする」。安全で、何度やっても同じで、退屈な操作。

実際に真だったこと　sync は一方向のミラーで、コピー先の余分なファイルを消す。これは文書化されているし、読み違えたのは自分の責任だ。鋭い角は別のところにあった。シンボリックリンク（別の場所を指す「参照」だけのファイル）は警告つきで飛ばされ、そのうえコピー先にあった実ファイルは消された。 リンク先が存在しない壊れたリンクでも同じことが起きた。そして終了コードは0だった。

検知すべき失敗は存在しない。このコマンドの定義では、何も失敗していないからだ。警告はログに出ている。しかし自動実行される処理が判定されるのはログではない。

直し　大事なものに対して sync は使わない。復元は絶対に消さない rclone copy でやる。ミラーを走らせる前に、逆方向の rclone check --one-way で「コピー先にしか無いファイル」を明示的に数える。約59,000ファイルのライブラリで4分かかるが、今は喜んで払う4分だ。

開発者に1つだけ頼めるとしたら　ファイルを飛ばし、しかもコピー先の対応ファイルを消した実行は、終了コード0で終わらないでほしい。専用の終了コードでも、最後に飛ばした件数を1行まとめてくれるだけでもいい。情報はすでに存在していて、ただ自動処理が読む唯一の経路に届いていない。

一般化　終了コード0の意味は「プログラムが、自分がやろうとしたことを終えた」だ。「あなたが望んだ結果になった」ではない。この2つがずれうる場所では、過程ではなく結果を測る別の確認が必要になる。

3. ファイアウォールを、ファイアウォールの内側からテストした#

症状　なし。それが問題。

信じていたこと　ufw でいくつかのポートを塞いだ。サーバー自身から自分の公開アドレスへ接続してみて、期待どおりの挙動だったので確認完了とした。

実際に真だったこと　塞ぐルールは「外部インターフェースに到着する通信」に対して書かれていた。サーバー自身から自分の公開アドレスへ出す接続は、そのインターフェースを通らない。ローカル経路を通り、ルールに出会わない。つまりこのテストは「到達できる」しか返せなかった。 検出するために存在していた故障を、構造的に検出できない。しかも危険な方向に外れる。全部問題なく見える方向だ。

直し　外部からの到達性の確認は、必ずサーバーではない別のマシンからやる。手間が1つ増えるが、省略はしない。

一般化　失敗しようのないテストはテストではない。 確認を信じる前に、「確認したい対象が壊れていたら、どんな結果が見えるはずか」を言葉にする。言葉にできないなら、何も確認していない。

4. 扉を閉めて、窓を開けたままにした#

症状　認証を要求するべき2つのサービスが、インターネットから到達できる状態だった。

信じていたこと　露出を見つけ、塞ぐルールを書き、ポートが閉じたのを確認し、次に進んだ。タスクは「完了」にした。

実際に真だったこと　書いたのは IPv4 のルールだった。このサーバーには公開 IPv6 アドレスもあり、Dockerは両方で待ち受けていた。IPv6 側は手つかずで、既定の「全部通す」のまま、ルールが1本もなかった。 2つのログイン画面は、自分が「直した」と思っていた期間ずっと、公開されていた。

ここでは有名な罠が2つ重なっていて、自分はどちらも知らなかった。ひとつ、Dockerは自分で転送ルールを書き、ufw に相談しない。 だから ufw status が何と言っていようと、公開したポートには届く。ふたつ、片方のアドレス体系に向けて書いたルールは、もう片方には単に存在しない。

直し　ネットワークのルールは両方のアドレス体系に書き、両方で確認する。到達性の確認にも IPv6 を明示的に含めた。そして、より大事なこととして、塞ぐルールを第一の防御にするのをやめた。サービスはループバック（そのマシンの内側だけに見えるアドレス）に bind し、外からはトンネル経由でだけ届く。ファイアウォールは2枚目の層にした。

一般化　自分が持っている失敗の中で、これが一番気分が悪い類だ。「解決した」と思っていて、実は半分しか解決していなかった。 未解決の問題より悪い。未解決ならまだリストに載っているが、半分解決した問題はもう消されている。

5. 検索パターンが見られなかった19本のポート#

症状　待ち受けポートの定期点検では、おかしなものは出なかった。あとで別のやり方で点検したら19本出た。

信じていたこと　外に開いているものを見るには ss -tulpn を実行して、ワイルドカードのアドレスで絞る。つまり grep 0.0.0.0。

実際に真だったこと　両方のアドレス体系で待ち受けているソケットは 0.0.0.0:ポート ではなく *:ポート と表示される。 探していた文字列は、その行にそもそも含まれていない。パターンは存在しないものを探して空の結果を返し、自分はそれを「露出なし」と読んだ。

加えて、露出はコンテナのポート公開からしか生まれないと思い込んでいた。出てきた19本はホスト側のプロセスで、自分の頭の中の地図にその区画がなかった。

直し　フィルタを反転した。「露出に当てはまるもの」を並べるのをやめ、全部出して、ローカルだと証明できるものを除外する。 残って、かつ見覚えのないものは、絞り落とさずに調べる。

一般化　点検はブロックリストではなくアローリストで書く。 「悪いと予想したもの」で作ったフィルタは、自分が既に想像できた問題しか見つけられない。「問題ないと確認したもの」で作ったフィルタは、想像していなかったほうを浮かび上がらせる。

6. フラグの位置を間違え、それを隠した0#

症状　検証を通ったはずのトンネル設定が、実は無効だった。

実際に真だったこと　cloudflared tunnel ingress validate --config FILE と打った。この --config は全体に効くフラグなので、サブコマンドより前に置かないといけない（cloudflared --config FILE tunnel ingress validate）。自分が置いた位置では、このフラグは未定義だ。そしてコマンドは何も検証しないまま終了コード0を返した。 自分はその0を「設定は有効」と読んだ。

このページで一番純粋な形の失敗がこれだ。未定義のフラグは0以外で終わるべきで、何も検証しなかった検証は、合格した検証と同じ見た目になってはいけない。

直し　「動かす」のではなく「検証する」道具については、自分が意図したファイルを本当に読んだかを先に確かめる。 やり方は、わざと壊した入力を食わせて、文句を言うか見る。壊したファイルに文句を言わないなら、そいつは自分のファイルを一度も見ていない。

一般化　検証ツールは、偽の合格が最も隠れやすい場所だ。合格した検証は、疑う材料になる出力を何も出さないからだ。既知の壊れた入力で、テストをテストする。

7. 1か月の故障を隠していた200 OK#

症状　サイトは平文のHTTPでは問題なく見える。暗号化された接続（HTTPS）だけ失敗する。

信じていたこと　サイトは動いている。数週間にわたって何度も確認して、毎回応答があった。

実際に真だったこと　独自ドメイン向けのTLS証明書（通信を暗号化するための証明書）の発行が、一度も完了していなかった。 平文のHTTPは完璧に動く。だからこそ調べなかった。見ているプロトコルが間違っていて、安心できる答えが返ってきていた。これが1か月続いた。

真因は2層下にあって、完全に自分のせいだった。公開の処理が毎回 force-push（履歴を作り直す強制的な反映）をしていて、証明書の発行手続きが毎回途中状態から振り出しに戻されていた。 自分は「ドメインを外して入れ直す」を10回以上試していて、それは何も解決していない。自分の直しを無かったことにする処理が、次に公開するたびに走っていたからだ。

直し　証明書の状態を「ページが開くか」ではなく問い合わせる項目として確認するようにした。gh api repos/OWNER/REPO/pages --jq '.https_certificate.state' が approved になっているかを見る。そして最後には、その証明書を経路から丸ごと外し、暗号化の終端を手前のCDN側に任せた。1か月詰まっていた問題が、DNSの変更が反映される時間で終わった。直しとは、修理ではなく削除であることがある。

一般化　2つある。ひとつ、症状が10回の修正を生き延びたなら、問題は自分が直し続けているものではない。 手を止めて、自分の直しを元に戻しているものを探す。ふたつ、テストしていない層からの成功応答は、テストしたい層についての証拠ではない。

8. 「だいたい同じ件数」は確認ではない#

症状　メール移行で、数千通を失いかけた。

信じていたこと　移行元と移行先の件数がだいたい一致している。移行完了。移行元の削除に着手した。

実際に真だったこと　6週間分のメールがまったく転送されていなかった。 合計の差が、自分の「だいたい」の許容範囲にちょうど収まる大きさだった。7,536通を復元できたのは、何か月も前に別の目的で取っておいたエクスポートが、たまたまゴミ箱に残っていたからだ。それは復元手順ではない。運だ。

直し　移行の確認は、合計ではなく1件ごとに一意の識別子を突き合わせる（メールなら Message-ID）。そして、コピーを実行した方法とは別の方法で移行先を確認するまで、移行元からは何も消さない。

一般化　合計の照合は、打ち消し合う誤りを隠す。500件コピーに失敗し、480件が重複していたら、合計は合っていてデータは壊れている。 確認は「失われたら困るものの粒度」でやらなければ意味がない。

9. 違う2つを測って、その数字を信じた#

症状　暗号化したストレージが暗号化なしの約15倍遅い、と測れてしまった（7.01秒 対 0.46秒）。その数字で構成を決めかけた。

実際に真だったこと　比べていた2つのマウントで、キャッシュと --vfs-read-chunk-size の設定が違っていた。測っていたのは暗号化の負荷ではなく、自分の設定の差だった。 条件を揃えたら、17MBのファイルで実際の差は1秒を大きく下回った。確かにコストはあるが、無視できる大きさだ。

直し　A/Bの比較は、まずAとBの設定の差分を取ることから始める。そして、同じ測定が再現するまで数字を信じない。

一般化　判断を後押しする数字は、そうでない数字より強く疑うに値する。 そして、驚くほど「大きい」効果は、発見であるより測り方の誤りであることが多い。自分は、存在しないコストを避けるために、より悪い設計を受け入れかけていた。

10. 3案を比較して、押していなかったボタン#

症状　ディスクが足りなくなってきた。そして数週間の比較検討。

信じていたこと　ディスクを超えて増えるなら、選択肢は3つ。古いデータをネットワーク越しのオブジェクトストレージへ退避する、別のストレージ製品へ移る、より大きいサーバーへ引っ越す。3案すべてをちゃんと評価した。1TBあたりの費用、取り出し時の課金、壊れ方、移行手順書まで。

実際に真だったこと　契約している業者の管理画面に「Extend SSD Storage」というボタンがあった。 再インストールなし、移行なし、あとはパーティションとファイルシステムを広げるコマンドを2本打つだけ。公式のヘルプにも書いてある。一度も検討していなかった。見つけたのは、手を止めて一番バカな質問をしたからだ — このディスク、単に大きくできないのか? 200GBを400GBにして、その日の午後に終わった。

自分が必要だった容量では、ディスク増設は1TBあたりで最も高い選択肢だ。それでも正解だった。他の案は月に数ドル安く、複雑さがはるかに高い。

直し　構成を比較する前に、今の構成に「単に増やせる退屈なパラメータ」がないかを確認する。

一般化　この11件で一番好きな失敗がこれだ。何も壊れていない。 自分が持っていた問題より難しい問題を、数週間かけて解いていただけだ。面白い解は退屈な解を押しのける。そしてこの規模では、退屈なほうが正しいことが多い。 付け加えておくと、正解を見つけた質問は、自分がうんざりして口にしたものだった。それまで自分が積み上げた分析の流れに、完全に逆らっていた。

11. 置き換えたはずの古い仕組みが、履歴に残していた秘密#

症状　非公開のgitリポジトリの履歴に、サーバーの秘密鍵、各サービスの設定ファイル、期限切れのAPIトークンが入っていた。

実際に真だったこと　それらのファイルが追跡されていたのは、ある時点ではコミットすることがバックアップの方法そのものだったからだ。その後、バックアップは暗号化したオブジェクトストレージに移した。移した時点で、追跡は不要になっていた。誰も外さなかった。新しい方法を用意する手順の中に「古い追跡を外す」が入っていなかったからだ。 古い仕組みは正しく動き続けていた。もう望まれていないことを、正しく。

直し　追跡から外し、必要なものは作り直した。そして今は一般的な規則として持っている — 仕組みを置き換えたら、古い仕組みが何をしていたかを明示的に点検して、止める。 移行のチェックリストは、新しいものを足すのは得意で、古いものを引くのが苦手だ。

一般化　危険なレガシーは、壊れているものではない。まだ動いているものだ。

いま実際に変えた習慣#

ベストプラクティスではない。上の11件から出てきた5つ。

成功の報告は、結果ではなく主張として扱う。 終了コード0、200 OK、「警告なし」、「プロセスは動いている」。どれも、自分が訊きたい問いより狭い問いに答えている。大事なものについては、それを生んだ経路とは別の経路で結果を確認する。

失敗がどう見えるかを先に言う。 確認を信じる前に、対象が壊れていた場合に見えるはずの出力を言葉にする。言葉にできないなら、その確認は演技だ。ファイアウォールの件が教えたことで、この5つで一番元が取れる。

何かを直した直後の自分を、最も疑う。 IPv6の件と証明書の件は、どちらも「解決済み」の問題だった。消した問題はもう見張られていない。だから半分の直しは、直していないより危険だ。 いまは「たったいま成功した」という気分の側からではなく、ゼロから確認し直す。

設計の前に、退屈なパラメータを探す。 これは大きくできないか。これは止められないか。修理ではなく削除できないか。すでに2回、頭の中で複雑なほうを作り終えたあとで、答えが「できる」だった。

失敗はその場で書く。 読者のためではない。2回目に遭遇したとき、自分が何を既に除外したのか思い出せなかったからだ。あるエラーコードは3回別々に診断して、3回別々の真因だった。4回目の夜を失わずに済んだのは、最初の3回が書かれていたからだ。このページも、その記録から書いた。記憶から再構成したものは1件もない。

14か月、サーバー1台、利用者2人、記録された失敗11件。いまも動いている。
