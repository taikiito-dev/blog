写真をGoogle PhotosからImmichに移す

Google Photosの全データ（32,218件、約119GB）を自前サーバーのImmichへ移した記録。

先に役割を書いておく。コマンドを書いたのはClaude（AnthropicのAIアシスタント）で、私は決める側をやった。 私はエンジニアではない。それでも32,218件は無事に移ったし、今も毎日見られている。

この分担はやってみると気持ちよかった。手順を考えなくていいぶん、「何を守るか」だけをじっくり考えられた。 だからこのページも同じ形にしてある。

  • 前半（判断） — 何を決め、何を選ばなかったか、後から見てどうだったか
  • 後半（手順） — 実際のコマンドと設定。Claudeが書き、自分の環境で実行して結果を確かめたもの

もしあなたもClaudeやChatGPTのようなAIを使えるなら、後半は自分の環境に合わせて出してもらったほうがいい。そのほうが新しいし、あなたの機械に合う。そのとき役に立つのが前半だと思う。 頼む前に決めておくことがいくつかあって、それは頼んでも出てこないからだ。

決定1 — Google Photosを消さなかった。今も消していない#

日付 2026年8月24日（移行実行）/ 判断は現在も継続中

迷ったこと 移行が終わったら、元のGoogle Photosは消すのか。消さないとお金を払い続けることになる。

採った案 消さない。並行運用のまま置いておく。 2026年10月の時点でも、Google・Immich・iCloudの3か所に同じ写真がある。

却下した案 移行確認後にGoogle側を削除して、ストレージプランを解約する。これが本来の目的だったので、却下したのは自分の当初計画だ。

なぜ却下したか 移行の直後、ブラウザで開いたら昔の写真がちゃんと時系列に並んでいた。嬉しかったし、成功だと思った。

ただ、そこで一度立ち止まった。自分が見たのは最初の画面だけだ。 32,218件を目で確認するのは、どうやっても無理だ。つまり確認できたのは「全部無事」ではなく「最初の画面は無事」のほうだった。

この2つは違う。違うと分かった時点で、消すのは後回しにした。

後から見た当たり外れ 当たり。しかも後から裏付けが出た。 1年後、別の理由でサーバーを乗り換えるときに新旧2台の写真を手で突き合わせたら、46件が片方にしか無かった。あのときGoogle側を消していたら、46件は消えていた。

自分は「写真が1枚消えても死なない」と思っていたが、実際に46という数字を見たときの気分は、想像していたものと全然違った。

残った教訓 移行の成功は、移行元を消したときに確定する。開いて見た瞬間ではない。 だから消すのを遅らせるのは、ケチでも臆病でもなく、確認の一部だ。お金で時間を買っていると考えればいい。

いま自分が持っている基準はこれだ。全件を突き合わせていないなら、移行は終わっていない。 そして全件の突き合わせは、人間がやる作業ではない。頼めばいい。自分がやるべきは「突き合わせたか」と訊くことだけだ。

決定2 — 公式のツールを使わなかった#

日付 2026年8月24日

迷ったこと 取り込みに何を使うか。Immichには公式のコマンドがある。

採った案 公式ではなく、有志が作った immich-go という別のツールを使った。

却下した案 公式ツール。

なぜ却下したか Google Photosから書き出したデータには、写真本体とは別に、撮影日時とアルバム情報が入った付属ファイルが一緒に入っている。公式ツールはこれを読まない。 読まないとどうなるかというと、アルバムの中身と正確な撮影日時が消える。

ここが自分の判断の分かれ目だった。写真のファイルが残っていても、撮影日時が消えたら自分にとっては失われたのと同じだと思った。2015年の写真が「2026年8月24日」になって全部一列に並ぶなら、それはもう自分の写真ではない。

非公式のツールを使うリスクは承知の上で選んだ。 公式が安全で非公式が危険、という一般論より、「何が失われるか」が具体的に分かっているほうを採った。

後から見た当たり外れ 当たり。 32,218件のうち、撮影日時やアルバムが紐づかなかったのは7件だけだった。

残った教訓 「公式か非公式か」は判断の軸にならない。「失敗したとき何が失われるか」が軸だ。 公式を選べば安心なのではなく、公式が守ってくれないものがあるなら、それは自分で守る対象になる。

この手の選択をClaudeに任せると、たいてい「公式」が返ってくる。無難だからだ。何が失われるかを訊くのは、こちら側の仕事だった。

決定3 — 本番実行の前に、数字を1回見ることにした#

日付 2026年8月24日

迷ったこと 3万件・119GBの取り込みを、いきなり本番で走らせるか。

採った案 先に「実際には何もしないが結果だけ出す」モードで一度走らせて、数字を見てから本番を決めた。

出た数字はこうだった。

Total Assets: 32218
Associated metadata: 32211
Missing metadata: 7
Errors: 0

この数字をどう読んだか 自分が怖かったのは1つだけで、「時系列が全部壊れる」ことだった。写真が数枚失敗するのは許せるが、3万件の日付が全部めちゃくちゃになったら復旧できない。

欠落7件という数字は、その恐怖に対する答えになっていた。7は「全部壊れる」とは違う。だから本番に進んだ。

ついでに却下した案 日付情報が無い写真も強引に取り込むオプションがあった。付けなかった。7件を救うために、他の32,211件の扱いを変えるのは比率が合わない。 7件は後で手で入れればいい（結局まだ入れていない）。

後から見た当たり外れ 当たり。 本番の結果も、エラーは2件だけだった。しかもログを見ると写真本体ではなく「アルバムを作れなかった」という付随的な失敗だけだった。

残った教訓 本番の前に、自分が何を恐れているのかを1つに絞る。 絞れていれば、見るべき数字が決まる。絞れていないと、出てきた数字を全部見て全部怖くなる。

自分がやったのは「32,218件のうち7件」という比率を読むことだけで、技術的な理解は一切使っていない。これは非エンジニアでもできる仕事で、しかも誰かがやらないといけない仕事だった。

決定4 — 再生成できるものは、守らないと決めた#

日付 2026年8月24日

迷ったこと バックアップに何を含めるか。

採った案 2つ決めた。

ひとつ、写真のファイルだけでなく、データベースも守る。 アルバムの構成、補正した撮影日時、顔認識の結果は、写真ファイルの中ではなくデータベースの中にある。写真だけ守ると、戻したときに「写真はあるが整理が全部消えている」状態になる。

ふたつ、一覧表示用の縮小画像と、変換済みの動画は、守らない。 これらはソフトが自動で作り直せるものだ。守る対象に入れると、バックアップの容量が無駄に膨らむ。

却下した案 「とりあえずフォルダごと全部」。これが一番簡単で、最初はそうしようとしていた。

なぜ却下したか 「全部守る」は、実は何も決めていないのと同じだと気づいた。容量が増えれば転送に時間がかかり、時間がかかれば失敗しやすくなり、失敗すれば守れなくなる。全部守ろうとすると守れなくなるという、逆向きの関係がある。

だから線を引いた。線は「作り直せるか」で引いた。作り直せるものは守らない。作り直せないものだけ守る。

後から見た当たり外れ 部分的に外れ。 線の引き方は正しかったが、それが毎晩ちゃんと動いているかを確認する仕組みを作っていなかった。

実際に起きたことはこうだ。バックアップは何か月も「成功」と報告していた。ある日、別の作業で件数を数えたら46件が取りこぼされていた。スクリプトが途中で止まっていて、それ以降が毎晩まったく実行されていなかった。静かに。

つまり自分は**「何を守るか」を決めて、「守れたことをどう確かめるか」を決めていなかった。** 前者だけでは半分だ。

残った教訓 バックアップの判断は2つあって、自分は1つしかしていなかった。

  1. 何を守るか — 作り直せないものだけ。これはできた。
  2. 守れたと、どうやって知るか — ここが空白だった。「成功」の報告を数か月信じていた。

いま自分が訊くようにしている質問はこれだ。「これが昨夜失敗していたら、私はどうやって知るんですか」。 答えが「気づきません」なら、そのバックアップは飾りだ。この質問は実装を知らなくてもできる。

決定5 — 自動化する前に、一度手で走らせた#

日付 2026年8月24日

迷ったこと 119GBの初回転送を、そのまま毎晩の自動実行に任せるか。

採った案 初回だけ手で実行し、しかも転送速度に上限をかけた。 完了を自分で確認してから、自動実行に組み込んだ。

なぜそうしたか 当時は自宅の回線を使っていた。119GBを全速で送ると、半日から丸1日、家のインターネットが使い物にならなくなる。それは避けたかった。

後から見た当たり外れ 当たり。しかも後から理由が増えた。 選んだときは回線の都合だけだったが、結果的に「初回を自分の目で見る」ことになったのが効いた。

自動で動いているものは、二度と見ない。だから初回を自動に任せると、人間が一度も結果を見ていない処理が毎晩走ることになる。初回だけ手でやっておけば、少なくとも1回は「うまくいっている状態」を自分の目で知っていることになる。比べる基準が手元に残る。

残った教訓 自動化は、一度手でやって結果を見たあとにする。 この順番にしておくと、あとで何かおかしいときに「前はこう見えていた」と言える。順番が逆だと、おかしいのかどうかも分からない。

当時ハマったこと（自分の不注意の記録）#

判断ではなく、単に自分が雑だった件も残しておく。同じことをやる人は同じように雑になると思うので。

書き出したファイルが2つ足りなかった Google側の書き出しは12個のzipに分割された。全部ダウンロードしたつもりで作業を始めたら、途中の2つが抜けていた。あとで気づいた。件数が多いときは、連番が最後まで揃っているかを作業開始前に数える。 これも「全部揃った気がする」で進めた失敗で、46件の件と同じ形をしている。

取り込み直後に壊れたと思って焦った 画面にエラーのような表示が出た。本体が壊れたかと思った。実際は、縮小画像の生成や顔認識といった後片付けの処理がまだ山ほど残っているだけだった。数時間待ったら正常になった。取り込み直後の異常な表示は、まず「まだ処理中ではないか」を疑う。

まだ終わっていないこと#

正直に書いておく。

iPhoneの写真は、まだiCloudにも入っている。 Immich一本にするには、iPhone側のiCloud写真をオフにして、Immichアプリの自動バックアップだけに切り替える必要がある。やっていない。

理由は決定1と同じで、Immichの自動バックアップが毎回ちゃんと動いていることを、自分はまだ確認できていないからだ。確認の方法が決まっていないものに、写真の主管を渡すつもりはない。

Apple純正の「写真」アプリ自体をやめるつもりはない。見る道具としては使い続け、保管の主管だけをImmichに置くという役割分担にする方針だ。

手順#

ここから下はClaudeが書き、自分の環境で実行して結果を確かめたものだ。2026年8月から9月の版で、実際にこれで32,218件が移った。

置いておく理由は2つある。ひとつは、作業の全体像と長さが先に分かること。「これは終わりがある作業なのか」は着手の前に知りたいことだと思う。見てのとおり7段階で、半日から1日の話だ。

もうひとつは、自分が使っているAIに「これと同じことをやりたい」と渡す材料になること。ゼロから説明するより、動いた実例を見せたほうが早い。版が新しくなっていれば、そのとき合った形に直してくれる。

前提の環境#

  • 常時起動しているLinux環境（自分の場合はWindows機の中でWSL2〈WindowsのなかでLinuxをそのまま動かす仕組み〉のUbuntu）
  • Docker Engine（ソフトを隔離された箱に入れて動かす仕組み）と docker compose が使える状態
  • ターミナル（文字でコマンドを打ち込む黒い画面）に抵抗がないこと

GPU（グラフィック処理用の高性能な部品）は必須ではない。無くても写真の保管・閲覧は問題なくでき、違うのは顔認識やあいまい検索の処理速度だけ。自分はたまたまゲーミングPCがあったのでGPUを使う構成にした。使わない場合は「GPUを使う場合」の節を飛ばしてよい。

Step 1: Immichを起動する#

mkdir ~/immich && cd ~/immich
curl -fL -o docker-compose.yml https://github.com/immich-app/immich/releases/latest/download/docker-compose.yml
curl -fL -o .env https://github.com/immich-app/immich/releases/latest/download/example.env
curl -fL -o hwaccel.ml.yml https://github.com/immich-app/immich/releases/latest/download/hwaccel.ml.yml

.env で最低限2点を変更する。

  • DB_PASSWORD — 既定のままだと誰でも推測できるので変える
  • UPLOAD_LOCATION — 写真の実ファイルの置き場所。既定のままで問題ない

セットアップ中に出てくる「Storage Template」（保存されるファイルの命名・フォルダ構造を人間が読みやすい形に変える機能）はオフのままにした。閲覧はImmichの画面経由が前提なので生ファイルの構造を読む必要が薄く、後から有効化すると全件の再整理が走って重くなる。

docker compose up -d
docker compose ps

4つのコンテナが healthy になれば成功。ブラウザで http://localhost:2283 を開いて管理者アカウントを作る。

GPUを使う場合（任意）#

  1. WSL2からGPUが見えることを確認（nvidia-smi）
  2. NVIDIA Container Toolkit を導入し、nvidia-ctk runtime configure --runtime=docker
  3. docker run --rm --gpus all ubuntu nvidia-smi でコンテナからも見えることを確認
  4. docker-compose.yml の immich-machine-learning のイメージタグ末尾に -cuda を追加し、hwaccel.ml.yml の cuda 側を有効化（既定の cpu 側をコメントアウト）

Step 2: 取り込みツールを入れる#

決定2のとおり、公式CLIではなく immich-go（使ったのは v0.32.0、開発者は simulot 氏）を使う。

curl -fL -o immich-go.tar.gz https://github.com/simulot/immich-go/releases/download/v0.32.0/immich-go_Linux_x86_64.tar.gz
tar -xzf immich-go.tar.gz
chmod +x immich-go

版によって配布ファイル名やオプション名が変わるので、実行前に ./immich-go --help を見ること。

Immichの管理画面（Account Settings → API Keys）でAPIキーを1つ発行しておく。

Step 3: Google側からデータを書き出す#

takeout.google.com で「Google フォト」だけを選んで書き出しを作る。形式はzip。準備ができるとメールが来る。

ここで連番を数える（「当時ハマったこと」参照）。自分の場合は12個に分割され、2つ取りこぼしていた。

Step 4: 長時間処理に備える#

数万件・100GB超のアップロードは何時間もかかる。ターミナルの窓を閉じると処理も止まるので、tmux（ターミナルの中にもう一つ独立したターミナルを作るツール）の中で実行する。

tmux new -s immich-import

元の窓を閉じても処理は動き続ける（戻るには tmux attach -t immich-import）。

Step 5: 何もしないモードで数字を見る#

./immich-go upload from-google-photos \
  --server=http://localhost:2283 \
  --api-key=<Step2のAPIキー> \
  --dry-run \
  ~/Downloads/takeout-*.zip

この出力をどう読んだかは決定3に書いた。

Step 6: 本番実行#

--dry-run を外すだけ。

./immich-go upload from-google-photos \
  --server=http://localhost:2283 \
  --api-key=<APIキー> \
  ~/Downloads/takeout-*.zip

自分の結果。

Uploaded successfully: 29408
Metadata updated: 30794
Discarded local duplicate: 1048
Errors: 2
Missing metadata: 7

1,048件は重複としてスキップされた（取り込み過ぎを防ぐ動きなので助かる）。エラー2件はログを見ると写真本体ではなく付随処理の失敗だった。

Step 7: バックアップに追加する#

決定4のとおり、データベースも守り、作り直せるものは守らない。

# データベースのダンプ
docker compose -f ~/immich/docker-compose.yml exec -T database \
  pg_dumpall --clean --if-exists --username=postgres | gzip > /tmp/immich-db.sql.gz

# 写真本体の同期（サムネイルと変換済み動画は除外）
rclone sync ~/immich/library "$B2_REMOTE/immich/library" \
  --exclude "thumbs/**" --exclude "encoded-video/**"

初回は決定5のとおり手動で、--bwlimit（転送速度の上限）を付けて実行し、完了を確認してから自動実行に組み込む。

⚠️ そして、このスクリプトが毎晩ちゃんと全ステップ走ったかを報告する形にしておくこと。 自分はこれを後回しにして、46件取りこぼした。詳しくはバックアップを「消されても戻せる」形にするに書いた。
