バックアップを「消されても戻せる」形にする

Backblaze B2への日次バックアップを「鍵を1本持ち出されても消されない」形に作り直した記録。サーバー上の鍵を18権限から5権限へ絞り、削除が伝播しない複製先を作り、サーバーの外に見張りを置いた。採った対策と見送った対策を前半に、手順と設定値を後半にまとめた。

この回の出発点は自分ではなかった。写真・パスワード・ファイルを自分のサーバーに集めたあと、毎晩クラウドストレージ(Backblaze B2)へバックアップを取る仕組みは動いていて、自分の側に困っていることは何もなかった。穴を見つけたのはClaude(AnthropicのAIアシスタント)で、サーバーに置いてある鍵の権限を数えてみろと言われて初めて、バックアップ本体まで消せる状態だと分かった。

この記事でやること — Backblaze B2への日次バックアップを「鍵を1本持ち出されても消されない」形に作り直す。サーバー上の鍵を18個の権限から実際に使う5個へ絞り、削除が伝播しない複製先を作り、複製が続いているかをサーバーの外から見張る。手順はページ後半にまとめた。

だから正直に役割を書いておく。穴を見つけたのはClaude、権限の調べ方と対策を組んだのもClaude、自分がやったのは「指摘を受けて、どこまでやるか」を決める側だ。 提示された案のうち何を採って何を見送ったか、それがこの記事の中身になる。

前提#

  • 常時起動しているLinux環境と、そこからrclone(いろいろなクラウドストレージへファイルを同期するコマンド)で日次バックアップを取っている状態
  • バックアップ先はBackblaze B2(安価なオブジェクトストレージ。1GBあたり月$0.005前後)
  • 構築の土台は自分の「サーバー」を持つとはどういうことか

指摘された穴#

事実だけ書く。サーバーに置いていたB2のアプリケーションキー(APIから操作するための鍵。権限を選んで発行できる)には18個の権限が付いていた。同期スクリプトが実際に使っていたのはlistBuckets, listFiles, readFiles, writeFiles, deleteFilesの5つだけで、残りは余分だった。

余分な中には、ファイルの版そのものを完全削除する権限、古い版をいつ消すかの設定(ライフサイクルルール)を書き換える権限、複製ルールを止める権限が含まれていた。つまり鍵を1本持ち出されたら、バックアップ本体も、それを守るはずの設定も、同じ1本で壊せる。「B2側に古い版を取っておく設定があるから荒らされても戻せる」という話は、設定ごと書き換えられる以上は成立していなかった。

これが自分では気づけなかった類の穴だ。毎晩のバックアップは成功し続けていたので、画面に出てくる情報だけ見ていれば何も問題はなかった。

決定1 — 指摘のうち、どこまでやるかを決めた#

日付 2026年9月下旬〜10月1日

迷ったこと 提示された対策は3つあった。(1) サーバー上の鍵を実際に使う5権限だけに絞る、(2) 削除が伝わらない複製先を用意する、(3) 複製が続いているかを見張る仕掛けをサーバーの外に置く。どこまで引き受けるか。

採った案 3つ全部やる。 いずれもハードウェアを増やさず、日々の手作業も増やさないで済むと確認できたため。鍵の差し替えと複製の設定は半日、見張りの実装はその続きで収まった。

却下した案 (1)だけで止める。

なぜ却下したか (1)と(2)はセットだとClaudeから説明された。鍵の権限だけ絞っても、複製という受け皿が無ければ元のデータが消えた時点で終わる。逆に複製だけ作っても、複製ルールを止める権限を持った鍵が残っていればルールごと止められる。片方だけでは意味がない、という説明に納得した。

残った教訓 対策を「大・中・小」で選ばせてくる話と、「2つで1つ」になっている話がある。後者を値切ると、払った分も無駄になる。

決定2 — ハードウェアをもう1台持つ案は採らない#

日付 2026年9月下旬

迷ったこと バックアップの定番は「もう1台の機械に3本目のコピーを持つ」だ。これを構成に入れるかどうか。

採った案 入れない。ハードウェア不要・手作業ゼロで回る形だけで組む。 この制約を先に置いてから、何ができるかを考えた。

却下した案 予備の機械を1台用意して、そこに3本目を置く。

なぜ却下したか 将来は拠点を移して身軽に暮らしたい。機械を持ち続ける前提の設計にはしたくなかった。

後から見た当たり外れ 制約を先に置いたことで案が絞れた。「機械は増やさない」を条件にすると、残るのはクラウド側の仕組みをどう組み合わせるかだけになる。結果として追加費用は複製分の月$0.70で、機械は1台も増えていない。

残った教訓 自分の側の制約(持ち物を増やしたくない、手を動かす作業を増やしたくない)は、技術の話より先に言ったほうがいい。先に言えば、出てくる案がその中から出る。

決定3 — 2段階認証アプリに、アカウント登録のいらないものを選んだ#

日付 2026年10月1日

迷ったこと 作業中に、より基本的な穴が出てきた。「2段階認証は済んでいる(ログインのたびにメールでコードが来る)」と認識していたが、これはBackblazeが既定で有効にしているメールMFA(多要素認証)だった。コードの送り先もパスワードリセットの送り先も同じメールアドレスなので、メールボックス1つで2要素が1要素に潰れる。TOTP(認証アプリが30秒ごとに生成する6桁コード方式)に切り替えるのは決まりとして、どのアプリを使うか。

採った案 Ente Auth のオフラインモード(アカウント登録なしで使える)。

却下した案 Google Authenticator。および、利用にアカウント登録が必要な認証アプリ全般。

なぜ却下したか Google Authenticatorは2点で不適だった。自分はGoogleアカウントを削除する方針なので同期機能が使えないこと、Google Playが載らない端末への移行を検討していること。そしてアプリ登録が必要なものだと、復旧手段がまた別の会社のアカウントに依存する。断ち切った鎖を作り直すことになる。

付随して決めたこと バックアップコードは生成してパスワードマネージャー(Vaultwarden)に保存した。ただしTOTPそのものは同じ金庫に入れない。 同じ場所に入れたら1要素に戻るので、TOTPはスマートフォンのアプリ側に置いた。

残った教訓 認証の道具を選ぶときは、普段の使い勝手ではなく失くした時にどこへ助けを求めることになるかで選ぶ。そこが他社のアカウントなら、依存を1本増やしたことになる。

決定4 — 別会社のストレージへもう1本は、今回は見送った#

日付 2026年10月1日

迷ったこと 残っている穴は自分でも分かる形で1つある。Backblazeというプロバイダ1社に依存していること。アカウントの凍結や会社都合に備えるなら、別会社のストレージへ追記専用でもう1本持つのが答えで、費用は月€4前後と見積もりが出ていた。

採った案 見送った。 未対策のまま残していることとして記録する。

却下した案 この流れで別会社のストレージも契約して、今回のうちに片付ける。

残った教訓 「やらなかった」を結果の欄に書いておくと、次に同じ話が来たときに最初から考え直さずに済む。

途中で踏んだもの#

決定とは別に、作業中の事故も書いておく。これは技術的な話というより、過去の自分が作った道具の仕様を忘れていたという型の失敗だ。

鍵の差し替えには、以前自分の環境向けに書いたrotate-b2-key.shというスクリプトを使った。これがrcloneの設定ファイルを丸ごと作り直す作りになっていた。同じ日の朝に、送信前に自前で暗号化するための設定ブロックをこのファイルに追加していたので、スクリプトはそれを知らずに消し、鍵の差し替えは成功したのに直後のバックアップが「設定ブロックが見つからない」で全滅した。

  • 教訓: 構成に新しい設定ブロックを足したら、そのファイルを書き換える既存スクリプトを洗い出す。 「鍵の差し替え」という名前から、設定ファイル全体を作り直しているとは読み取れなかった。
  • もう1つ: 設定ファイルはroot用と一般ユーザー用の2箇所にあり、復旧を片方だけやって放置していた。バックアップはrootで動くので「成功」と出続け、一般ユーザーで実行したときだけ静かに失敗する状態になっていた。「両方必要」と書いた手順は、実施後に必ず両方を実測で確認する。

もう1つ、鍵そのものの扱いで実際にやった失敗。作業中にターミナルの出力をそのままAIチャットに貼ってしまい、鍵の本体が会話ログに残った。同日中に再発行と旧鍵の削除で無効化したので実害はなかったが、鍵を発行するコマンドの出力はどこにも貼らない。確認は権限の一覧だけを出すコマンドで行う(後半の手順に書いた)。

最後の1本の置き場は、どの構成でも残る#

この構成でも閉じない循環が1つ残る。アカウントに入るには認証アプリが必要で、アプリを失くした時の救済はパスワードマネージャーにあり、そのパスワードマネージャーは自分のサーバーの上で動いている。自前で持つほど、「最後の1本をどこに置くか」という問題に必ず行き着く。 パスワードの移行の記事で書いたのとまったく同じ構造で、答えはいつも「デジタルでない場所にもう1箇所持つ」になる。

手順#

ここから先はClaudeが考え、自分の環境で実行して結果を確かめたもの。設定値の選び方や仕様の比較も、判断したのはClaude側だ。残しておく理由は2つある。(1) 着手する前に作業の全体像と長さが分かる。(2) 読者が自分のAIに「これと同じことをやりたい」と渡す材料になる。

1. 鍵の権限を必要最小限にする#

サーバー上の鍵を、実際に使う5権限ちょうどの新しい鍵に差し替える。

制約: B2のWeb管理画面の鍵発行UIでは権限を細かく選べない。 「読み書き」のような粗い単位しかないので、b2コマンド(Backblaze公式のCLI = コマンドライン操作ツール)が必須になる。全権限を持つマスター鍵を扱う作業なので、サーバー上ではなく手元のPCから実行した。

b2 account authorize
b2 key create --bucket <バケット名> <鍵の名前> \
  listBuckets,listFiles,readFiles,writeFiles,deleteFiles
b2 key list --long     # 権限が5つちょうどか確認
b2 key delete <旧鍵のID>
  • b2 account authorizeとb2 key createの出力は、どこにも貼り付けない。 鍵の本体(パスワード相当の文字列)が含まれる。確認はb2 key list --longで行うのが正しい(鍵のIDと権限しか出さず、本体は出ない)。
  • 鍵の状態確認はWeb管理画面を信じない。 削除済みの鍵が残って見えたり、新規作成した鍵が出てこなかったりした。b2 key listを正とする。
  • この手順は次の2とセット。1をやらずに複製ルールだけ作っても、複製ルールを止める権限を持った鍵でルールごと止められてしまう。

設定ファイルを書き換えるスクリプトの直し方#

丸ごと上書きをやめて、該当する2行だけを置換する形に直した。加えて書き込む前に「設定ブロックが減っていないか」「新しい鍵IDが入ったか」を検査し、1つでも失敗したら一切書かずに中止するようにした。

root用と一般ユーザー用の両方を確認するには、セクション名だけを出すコマンドを使う。値が出ないので安心して結果を見られる。

grep "^\[" <設定ファイル1> <設定ファイル2>
  • おまけの罠として、ssh サーバー 'bash -s' <<'EOF'形式のヒアドキュメント(複数行のスクリプトを流し込む書き方)はsshの標準入力と競合して出力が二重化し、成功したのか失敗したのか読めなくなった。サーバー操作は1行のssh サーバー '...'に分解して1つずつ流すのが確実だった。

2. 削除が伝播しない複製先を作る#

B2にはCloud Replicationという、バケット(ストレージ上のフォルダのような入れ物)の内容を別のバケットへ自動複製する機能がある。決定的な仕様はこれ。

削除と hideマーカー(B2が「削除された」印として置く目印)は複製されない。

つまり複製先は、構造的にappend-only(追加だけができて削除が伝わらない)なミラーになる。元のバケットでファイルが消されても、複製先には残り続ける。これが対策の本体になる。

複製元を読む鍵・複製先に書く鍵はB2が自動で2本発行し、どちらもB2の内部にしか存在しない(サーバー上に置かれない)。

同一アカウント内の別バケットで足りるかどうか#

Claudeの判断は「足りる」で、理由はこうだった。

  • サーバー上の鍵は元のバケットに限定されているので、別バケットには構造的に届かない。
  • 別アカウントが必須になるのは「別リージョンへ複製する場合」だけ。 同一アカウント・同一リージョンの別バケットへの複製は普通にできる。
  • 別アカウント構成と差が出るのは「B2のログイン自体を乗っ取られた場合」と「リージョン障害」の2つ。前者についてはTOTPへの切り替えのほうが本質的な対策になる。

複製先のライフサイクル設定の落とし穴#

  • 🔴 「Keep only the last version」(最新の版だけ残す)を選んではいけない。 上書き攻撃を受けた瞬間に正常な旧版が消え、複製先を用意した意味がなくなる。必ずUse custom lifecycle rulesを選ぶ。
  • 🔴 Days Till Hideは必ず空にする。 ここに数字を入れると、現役のバックアップ本体が自動削除される。埋めるのは「古い版を何日後に消すか」の1箇所だけ。

保存期間を180日にした計算#

この環境では古い版を180日で削除に設定した。毎晩上書きされるデータベースのダンプ(写真サーバー188MB + ファイルサーバー18MB + 認証サーバー13MB ≒ 日220MB)が積み上がって年80GB増える計算だったため。180日なら約40GBで頭打ちになる。

保護が弱まるわけではない——削除は複製されないので、消されたファイルにはこの設定は無関係。上書きのほうは次の3の見張りが1週間以内に検知する。

初回コピーの実績#

複製元141.5GB・118,503ファイルに対して、複製先は149.0GB・118,976ファイルで完了。複製先のほうが大きいのは設計どおり(元で消えた・上書きされたファイルが残り続けるので膨らむ)。初回コピーは数日かかった。

  • 初回コピーの進捗はAPIでは測れない。 B2が複製の状態フラグを付けるのはルール作成後に新規アップロードされたファイルだけで、既存ファイルの後追いコピー分は全件「未設定」のまま。進捗はWeb管理画面の複製先バケットのファイル数で見るしかない。
  • 初回コピー完了を待つ必要はない(見張りの判定は「減った/増えていない」なのでコピー中に誤報は出ない)。ただしライフサイクル設定は初回コピー完了まで触らない——コピー中の変更は直後のファイルが消える危険があると公式ドキュメントに明記されている。
  • コストは複製分で月$0.70。複製の転送料は無料。

3. サーバーの外に見張りを置く#

複製が本当に続いているかを誰も見ていなければ、仕組みは静かに壊れる。そこでデッドマンスイッチ(定期的な生存信号が途絶えたら警報を出す仕掛け)を用意した。

肝はサーバーの外で動かすこと。サーバー監視には別途Uptime Kumaを使っているが、これはサーバー自身の上で動いているので、サーバーごと死んだら自分の死を通報できない。

実装はGitHub上の非公開リポジトリ1つ + GitHub Actions(GitHubが提供する、決めた時刻やイベントでスクリプトを自動実行する仕組み)。週1回、複製先バケットを走査して、次のどれかに当たったら通知アプリへ通報する。

  1. ファイル件数が前回より減った
  2. 合計サイズが前回比1%を超えて減った
  3. 21日間まったく増えていない
  4. B2へ接続・認証できない

観測値はリポジトリ内のJSONファイルにコミットして、次回の比較基準にする。外部ライブラリは使わず標準ライブラリだけでB2のAPIを直接叩く作りにした(依存が増えると、それ自体が壊れる原因になる)。見張り用の鍵は複製先バケット限定・読み取り専用なので、こちらはWeb画面の発行UIで作れる。

  • 件数の減少は「複製先を直接触られた」ことのシグナルとして意味が強い(削除は複製されないので、正常運用では減らない)。
  • 上書きの検知は不完全だと正確に理解しておく。同サイズ・より大きいサイズで上書きされた場合は検知できない。ただしその場合も版管理で旧版が残るので復元は可能で、守りは版管理側が担っている。
  • GitHub Actionsの定時実行は大幅に遅れる。 0 1 * * 1(毎週月曜01:00 UTC)と書いたジョブが実際に走ったのは06:16 UTCで、5時間16分遅れだった。:00は最も混雑する分なので、奇数分(17 1 * * 1など)にずらすと改善する。週次監視なら遅延自体は無害だが、時刻を当てにした説明を書かないこと。
  • 通報が空振りする状態で放置してはいけない。 鍵をGitHubのSecrets(リポジトリに暗号化して保存する秘密情報)に登録する前に初回の定時実行が走り、認証情報が無くて失敗した。設計どおりの挙動だが、これを放置すると毎週失敗通知が来て、デッドマンスイッチの警報を無視する習慣がつく。それが一番の実害。

4. メールMFAからTOTPへ切り替える#

Backblazeが既定で有効にしているメールMFAは、コードの送り先とパスワードリセットの送り先が同じアドレスになる。アカウント設定からTOTPに切り替え、バックアップコードを生成して保管する。

  • バックアップコードはパスワードマネージャーへ。TOTPそのものは同じ金庫に入れない。
  • バックアップコードは、デジタルでない場所にもう1箇所持つのが本来。これはまだやっていない。

一番言いたいこと#

この回で自分がやったのは、穴を見つけることではない。見つけてもらった穴について、どこまでやるかを決めることだった。3つの対策は全部採り、機械を1台増やす案は採らず、別会社のストレージへの2本目は見送った。

そして毎晩のバックアップは、指摘を受ける前も後も変わらず成功していた。画面に出てくる情報だけ見ていれば、何も問題はなかった。 だから自分の使い方としては、こうなる——自分では気づけない穴があるという前提で道具を使い、指摘が来たら、そこから先の取捨は自分でやる。 全部任せるのでも、全部自分で見るのでもなく、その分担でいい。
